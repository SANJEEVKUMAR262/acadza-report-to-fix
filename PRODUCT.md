# Product Decisions — Acadza Report → Fix Loop

## Problem

Students report errors in educational questions, but reports may be duplicated, incomplete, incorrect, or unrelated to question content. Reviewing them manually is time-consuming, and automatically changing questions creates academic and operational risks.

## Product Goal

Help faculty identify genuine defects, understand supporting evidence, and make informed correction decisions without allowing unverified changes to the question bank.

## Key Design Decisions

**1. Question-centered review**

Reports are linked to their original questions, allowing multiple complaints about the same question to be considered together. The dataset contains 44 reports referencing 39 distinct questions.

**2. Separate diagnosis from correction**

Each assessment records a verdict, issue category, evidence, confidence, student-facing response, and optional proposed edit. Identifying a defect does not automatically authorize changing the question.

**3. Faculty-controlled approval**

The interface provides Approve, Reject, and Needs Review actions. Approval is restricted to validated, unapplied correction proposals routed for faculty review. Approval records a decision; it does not automatically edit the original question bank.

**4. Evidence-first explanations**

Faculty can inspect the original question, existing solution, assessment evidence, and proposed changes before deciding. Student-facing responses explain the assessment outcome.

**5. Safety against untrusted content**

Student reports are treated as data rather than instructions. The system includes proposal-validation checks and sanitized question rendering. Ambiguous, incomplete, or unsupported corrections remain subject to faculty judgment.

## Trade-offs

- **Local audit history:** Browser localStorage enables a lightweight demonstration but does not provide shared, authenticated, or durable server-side review records.
- **Conservative approval:** Some legitimate issues cannot be approved until a concrete correction is validated.
- **Prepared assessments:** Precomputed results make the dashboard fast and reproducible, but the interface does not perform live AI inference.
- **Human-assisted review:** The API test encountered insufficient quota, so completed assessments were human-assisted rather than successfully generated by the intended model.

## Success Criteria

A useful review should clearly identify the reported issue, preserve original content, provide checkable evidence, propose only defensible edits, and require faculty oversight before any correction is applied.

## Next Improvements

Add authenticated faculty accounts, shared audit storage, question-level decision synchronization, and a controlled publishing workflow for approved corrections.
